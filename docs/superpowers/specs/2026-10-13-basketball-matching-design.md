# 농구 게스트 매칭 서비스 상세 설계

- 작성일: 2026년 10월 13일, 한국 시간
- 수정 근거: 초기 플랫폼 수수료 0%, 결제 유예·모집 안내·알림, 앱을 구상했다는 추가 답변
- 근거: 사용자 인터뷰와 승인받은 첫 설계안
- 방식: 기존 HTML의 화면 스타일과 이용 흐름을 활용한다. 기존 웹 코드를 설치 앱 코드로 그대로 재사용할 수 있다고 가정하지 않는다.
- 상태: 2026년 10월 13일 사용자 검토 승인. 3.2절은 첫 구현·테스트의 기본값이며 실제 영업 정책·과금·계약 조건과 구분한다.
- 첫 결과물: iOS·Android 설치 앱을 주력으로 웹도 함께 제공한다. 실제 농구장 연결, 여러 회원의 모집·신청·수락, 테스트 결제·환불을 연결한다.

## 1. 한 페이지 요약

1. **목적**  
   서울·인천의 실내 농구에서 개인이 기존 팀의 게스트 모집에 참여한다. 핵심 불편은 근방의 경기·장소·시간을 계속 확인하고 글마다 열어봐야 했던 수고다. 야외 커뮤니티는 확장 후보다. 초기 모집팀은 아직 연결되지 않았다.

2. **첫 화면**  
   출발 위치·이동수단·허용 이동 시간·날짜와 시간대를 저장하고 접속할 때 맞는 경기를 보여준다. 이동 시간은 도보·환승을 포함한 경로의 예상 총시간이다. 지하철 30분, 자동차 15분, 원정 시 최대 40~60분은 개인별 선택 예시다. 원정의 40분을 하한으로 만들어 가까운 경기를 제외하지 않는다.

3. **목록 정보**  
   장소·시작/종료 시간·예상 이동 시간, 포지션·남은 자리, 경기 방식·교대 방식, 주장의 조율 방식을 강조한다. 기본 참가비와 총결제액도 표시한다. 총 대관 시간에서 개인 출전 시간을 추측하지 않는다.

4. **시설과 권한**  
   운영자 등록 시설과 승인된 팀의 주장·총무가 검색 또는 주소·핀으로 추가한 시설을 함께 사용한다. 새 시설의 모집글은 확인 상태를 표시해 공개한다. 시설 정보 확인, 팀 승인, 해당 경기 대관 확보는 별도로 관리한다. 운영자 승인은 안전 보증이 아니다.

5. **신청과 결제**  
   신청 → 주장 수락 → 자리 임시 확보 → 결제 → 참가 확정으로 연결한다. 기한 만료·취소 시 자리를 반환하며 서버와 DB가 정원·금액·상태를 관리한다. 첫 검증은 실제 돈이 오가지 않는 테스트 결제·환불이다.

6. **환불과 수익**  
   팀은 서비스가 제공한 환불 정책 중 하나를 선택하고 참가자는 신청·결제 전에 확인한다. 신청 당시 조건을 보존한다. 주최자가 취소하거나 경기 방식 변경으로 참가자가 불참을 선택하면 전액 환불한다. 초기 플랫폼 수수료는 0%로 두고 이용을 검증한다. 팀의 참가비는 별개다. 향후 플랫폼 수수료는 기본 참가비의 5~10%를 참가자·팀이 반반 부담하는 안이며 도입 시점은 아직 정하지 않았다. PG 비용은 외부 결제 업체에 내는 별도 비용이고 부담 주체는 견적 후 정한다.

   | 적용 단계 | 기본 참가비 | 전체 플랫폼 수수료율 | 참가자 결제액 | 팀 정산 기준액 | 플랫폼 수수료 매출 |
   |---|---:|---:|---:|---:|---:|
   | 초기 | 10,000원 | 0% | 10,000원 | 10,000원 | 0원 |
   | 향후 예시 | 10,000원 | 5% | 10,250원 | 9,750원 | 500원 |
   | 향후 예시 | 10,000원 | 10% | 10,500원 | 9,500원 | 1,000원 |

   위 결제·팀 금액은 PG 비용 미반영 계산 예시이고 플랫폼 수수료 매출은 순이익이 아니다. 실결제의 최종 금액은 PG 부담 방식 확인 후 확정한다. 테스트 표시가 실제 과금 시작이나 실정산 승인을 뜻하지 않는다.

7. **구현·검증**  
   iOS·Android 설치 앱을 주력으로 웹도 함께 제공한다. 회원·모집·신청·결제 상태는 공통 서버에서 관리한다. 알림함에는 공통 기록을 남기고 앱·웹 푸시는 사용 경로로, 카톡은 중요한 안내에 한정한다. 참가자 결제 알림과 주장 미처리 신청 알림은 최대 30분, 인원 부족 알림은 경기 시작 전 마지막 30분 동안 5분 간격으로 제한한다. 무료 범위와 외부 설정을 확인하고 양 OS의 로그인·지도·결제 복귀·알림, 공유 상태·정원·중복 환불을 검증한다.

## 2. 세 줄 요약

1. iOS·Android 앱과 웹에서 저장 조건에 맞는 경기·참여 판단 정보를 목록에 바로 보여준다.
2. 승인된 팀의 모집·수락과 테스트 결제·환불을 하나의 흐름으로 연결한다.
3. 초기 플랫폼 수수료는 0%이며, 향후 5~10% 반반 부담과 PG 비용·실결제 계약은 별도로 결정한다.

## 4. 개인의 경기 탐색

1. 공개 모집글은 로그인 없이 둘러볼 수 있다. 계정에 조건 저장·신청·모집할 때 로그인한다.
2. 카카오 로그인 후 내부 회원 ID로 소유권을 연결한다. 이메일을 필수 식별자로 사용하지 않는다. Supabase 카카오 제공자의 “Allow users without an email” 설정을 적용하고 이메일을 제공하지 않은 계정의 첫 로그인·재로그인에서도 같은 내부 회원 ID와 저장 조건이 유지되는지 검증한다.
3. 출발 기준은 역·장소 검색 또는 지정 위치다. 정확한 집 주소 입력은 필수가 아니다.
4. 이동수단·최대 예상 시간, 날짜·요일·경기 시작 시간 범위, 포지션을 저장한다. 종료 시각 상한은 추가 조건이다.
5. 평일 18시 이후는 빠른 선택 버튼이다. 퇴근 시각과 경기 참여 가능 시각이 같다고 가정하지 않는다.
6. 실제 경기 일시·모집 상태·포지션을 먼저 판정하고 후보의 경로 소요시간을 조회한다.
7. 지하철 조건은 지하철 경로와 해당 경로의 도보를 사용한다. 버스 경로를 지하철 결과로 섞지 않는다.
8. 예상 총시간이 설정한 최대 시간 이하면 조건 충족이다. 미충족·미확인을 분리한다.
9. 호출 실패·경로 없음·좌표 미확정은 사유와 함께 표시하며 0분 또는 조건 충족으로 바꾸지 않는다.
10. 시작 시각 가까운 순으로 제안한다. 조건 충족 경기가 없으면 조건 수정 안내를, 미확인 경기는 별도 확인 구역과 길찾기를 제공한다.

### 4.1. 카드와 상세

카드에는 날짜·시작/종료·장소·예상 총 이동 시간, 모집 포지션별 자리, 경기 방식·교대 방식, 주장 조율 방식, 기본 참가비·수수료·총결제액, 팀·시설 확인 상태를 표시한다.

주최자가 근거를 설명할 수 있을 때만 개인 예상 출전 시간을 입력하고 “주최자 예상·변동 가능”으로 표시한다. 미입력값을 총 대관 시간이나 인원수로 계산해 채우지 않는다.

상세에는 시설 안내·출입·집합 위치, 전체 예정 인원·팀 수, 게스트 팀 구성·교대 설명, 대관 확보에 관한 주최자 기재, 정책과 신청서가 포함된다. 최초 팀의 후기·진행 횟수를 예시에서 실제 기록으로 옮기지 않는다.

## 5. 시설·팀 승인·운영 관리

### 5.1. 시설 등록

| 운영자 등록 | 공식 안내 등 확인 가능한 근거로 이름·주소·좌표·실내 농구 용도를 등록 |
| 지도 검색·선택 | 승인된 주장·총무가 장소를 선택하고 시설 정보를 보충 |
| 검색에 없는 시설 | 이름·주소·핀 또는 좌표와 등록 근거를 추가 |

등록자·방식·근거·확인 시각을 남기고 중복 장소 후보를 표시한다. 위치 확인, 실내 농구 용도 확인, 주최자 기재, 오류 제보·재확인 상태를 구분한다. 주소 확인만으로 샤워실·주차·바닥·시설 상태를 확인했다고 표시하지 않는다.

미확인 시설도 승인 팀의 모집에 사용하되 확인 상태를 유지한다. 시설 운영시간·예약 안내는 그 팀의 대관 확보 증거가 아니다.

### 5.2. 팀 승인과 담당자

1. 회원은 팀 등록을 요청한다.
2. 운영자는 팀 정보·담당자 연락 경로와 팀 활동 또는 이용 시설의 근거를 확인하고 승인·보완 요청·반려한다.
3. 확인한 항목·시각을 남긴다. 회원가입 정보만으로 자동 승인하지 않는다.
4. 승인 팀의 활성 주장·총무만 자기 팀 모집글·신청을 관리한다. 구성원·역할 변경도 권한과 기록으로 관리한다.
5. 회원이 자기 프로필의 역할값을 바꿔 모집 권한을 얻을 수 없다.
6. 운영자는 모집 권한·게시를 중단할 수 있다. 기존 당사자의 신청·결제·환불 기록과 처리 경로는 유지한다.

연락처는 필요한 운영 확인·당사자 소통 범위에서 사용한다. 공개 목록에 일괄 노출하지 않는다. 카카오 로그인·팀 승인·시설 확인은 범죄나 사고가 없다는 보증이 아니다.

### 5.3. 모집글과 변경

필수 정보는 시설·집합 위치, 고정 시작/종료 시각, 경기 방식·전체 인원·팀 수, 기존 예정 인원과 포지션별 게스트 수, 기본 참가비·정책, 교대·게스트 구성·주장 조율 방식, 주최자의 대관 확보 기재다.

인원은 경기 전체 기준임을 표시해 주최팀 정원과 혼동하지 않게 한다. 5대5 등 방식에 필요한 인원과 전체 계획의 관계를 검증한다.

신청 후 장소·일시·금액·정책의 직접 변경은 제한하는 안이다. 필요한 변경은 기존 경기 취소·신청자 처리 후 새 모집글로 연결한다. 경기 방식 변경은 6.1절의 전용 안내·기록·불참 전액 환불 경로로 처리한다. 설명 보충도 이력을 남긴다. 회원 제보와 운영자의 수정·숨김·중단 사유를 관리한다.

## 6. 신청·수락·자리·결제

| 참여 상태 | 의미 | 자리 |
|---|---|---|
| 신청 대기 | 주장 판단 대기 | 차감하지 않음 |
| 수락·결제 대기 | 기한까지 임시 확보 | 유효 기간 동안 차감 |
| 결제 확인 중 | 기한 이전 서버 검증·접수를 마친 승인 요청의 PG 결과 확인 중 | 결과 정리까지 보류 |
| 참가 확정 | 서버가 정상 결제 확인 | 차감 |
| 거절 | 주장 거절 | 차감하지 않음 |
| 기한 만료 | 결제 대기 만료 | 반환 |
| 참가 취소 | 취소 접수·확정 | 반환, 환불 상태 별도 |

1. 수락 시 서버·DB가 팀 승인, 담당자 권한, 모집 상태·일시·전체 정원·포지션 자리를 확인한다.
2. 마지막 자리 수락은 원자적으로 처리해 동시 요청으로 정원을 초과하지 않는다.
3. 신청 포지션을 다른 남는 포지션에 자동 배정하지 않는다.
4. 결제 유예는 수락 후 30분과 경기 시작 중 빠른 시각이다. 다음 조회·작업에서도 만료를 판정한다.
5. 신청자만 주문을 생성하고 서버가 금액·정책 버전을 보존한다.
6. 앱·웹 클라이언트의 금액·결제 성공 표시는 확정 근거가 아니다. PG 승인·조회에서 주문 연결과 금액을 확인한다.
7. 승인 재시도·중복 통지가 중복 금액·자리 변경을 만들지 않게 한다.
8. 결제 기한은 클라이언트의 클릭·터치나 PG 응답 도착 시각 대신 서버의 검증·접수 시각으로 판정한다. 기한 이전에 유효한 승인 요청을 접수하면 결제 확인 중으로 전환하고, 결과가 기한 뒤 도착해도 응답 지연만으로 만료시키지 않는다. 기한 시각과 같거나 뒤에 새로 접수한 요청은 승인하지 않는다. 결과 불명확은 조회·재처리 상태로 남긴다. 유효한 기한 내 요청 없이 실제 승인된 예외나 경기 취소로 참여가 불가능해진 경우는 강제 참가 확정하지 않고 테스트 취소·환불 또는 운영 확인 대상으로 처리한다.

결제·환불·참석 여부는 참여 상태와 별도로 관리한다. 취소된 참가자의 자리를 환불 처리 중이라는 이유만으로 계속 묶지 않되, 결제 승인 여부 자체가 불명확하면 성공·실패를 추측하지 않는다.

### 6.1. 모집 현황 안내

경기 시작 30분 전 안내는 경기 진행 최소 인원과 게스트 모집 목표를 구분한다. 예를 들어 5대5 경기에서 기존 인원 8명·게스트 목표 4명에 게스트 2명이 참가 확정되었다면 전체 10명으로 5대5는 가능하지만 게스트 목표에는 2명이 부족하다. 전체 9명이라면 예정한 5대5의 진행 최소 인원도 부족하다.

안내 문구는 “모집 목표까지 2명 남음”과 “진행 최소 인원까지 1명 부족”을 구분한다. 결제 대기·결제 확인 중인 신청을 참가 확정 인원으로 표시하지 않는다. 남은 모집 자리는 확정자뿐 아니라 유효한 결제 대기·확인 중의 자리 보류도 반영하고, 진행 판단용 인원 표시와 혼동하지 않는다. 시작 30분 전 진행 최소 인원도 부족하면 주장이 진행·취소를 결정하고 참가자에게 안내한다. 모집 목표만 남은 상태를 같은 취소 판단으로 처리하지 않는다.

담당자 안내는 “게스트 확정 2명·결제 대기 2명·신규 모집 가능 0명”처럼 상태를 함께 표시한다. 자리가 전부 보류 중이면 부족한 확정 인원만 보고 같은 수의 새 게스트를 중복 모집하도록 안내하지 않는다.

최소 인원 미달만으로 자동 취소·환불하지 않는다. 주장이 취소하면 기존 팀 취소 정책의 전액 누적 환불 목표를 적용한다. 주장이 진행을 선택했다는 사실만으로 원래 경기 방식의 진행 가능성이 확인된 것으로 표시하지 않는다.

플랫폼이 현장 경기의 실제 진행·참석을 실시간 검증했다고 표시하지 않는다. 진행 상태는 “주최자가 취소를 안내함”, “주최자가 4대4 진행을 안내함”처럼 출처와 안내 시각을 표시한다. 기존 팀 인원은 주최자의 예정 인원, 게스트 확정 인원은 서비스 신청·결제상 인원이며 실제 출석과 구분한다.

예정한 5대5가 어려워 4대4로 진행한다면 주최자가 변경 내용을 안내한 뒤 진행한다. 기존 모집글의 경기 방식을 조용히 덮어쓰지 않고 원래 방식·변경 방식·사유·담당자·시각을 기록하며 해당 신청자에게 안내한다. 4대4 안내를 확인하지 않았다고 다시 동의한 것으로 표시하지 않는다.

원래 조건으로 신청했던 참가자가 변경 때문에 불참을 선택하면 개인 사정 취소의 시간별 정책 대신 전액 누적 환불 목표를 적용한다. 미결제자는 불참·자리 반환만 처리하고 PG 환불을 만들지 않는다. 불참 후 바뀐 경기 방식의 부족 인원을 다시 계산한다. 한 번 공지한 변경으로 최소 인원이 확보되었다고 가정하지 않는다.

첫 테스트의 자동 불참 선택 구간과 늦은 현장 변경 처리는 3.2절의 제안값으로 둔다. 안내 시각·변경 버전·대상 신청·불참 선택 시각을 보존한다. 현장 진행과 공지가 다르다는 제보나 시작 후 변경은 운영자 확인 경로로 남기며, 시간 구간을 넘겼다는 이유만으로 개인 사정의 무환불 취소로 자동 분류하지 않는다.

사용자가 정한 5분 단위 알림 대상은 결제 대기 중인 참가자 본인과 주장이다. 참가자에게는 남은 결제 시간과 결제 화면을 안내한다. 주장에게는 인원 부족과 판단 대기 신청을 안내해 모집·신청 판단을 돕는다. 모든 참가자에게 같은 인원 부족 알림을 5분마다 보내는 안으로 해석하지 않는다.

결제 완료·취소·만료 후 해당 참가자의 결제 독촉을 중단하고, 결제 확인 중에는 중복 결제를 유도하지 않는다. 주장이 처리한 신청은 대기 알림에서 제외한다. 주장의 부족 인원 알림과 판단 대기 신청 알림은 같은 경기의 현재 상태를 함께 보여줄 수 있다.

### 6.2. 알림함·전달 경로·반복 구간

| 경로 | 역할 | 준비·동작 |
|---|---|---|
| 서비스 알림함 | 당사자의 공통 기록 | 앱·웹에서 같은 회원의 안내·읽음·처리 상태 확인 |
| 설치 앱 푸시 | iOS·Android 앱 이용자 안내 | 기기 등록·수신 허용, 누르면 해당 경기·신청·결제 화면으로 이동 |
| 브라우저 푸시 | 웹 이용자 안내 | 브라우저 지원·수신 허용·구독 설정, 앱 푸시와 별개 |
| 카카오 알림톡 | 수락·참가 확정·경기 취소·경기 방식 변경 같은 중요 안내 | 비즈니스 채널·공식 딜러사·템플릿 심사·연락 경로·비용 확인 후 연결 |

카카오 로그인만으로 서비스가 회원에게 자동 알림을 발송할 수 있다고 가정하지 않는다. 일반 메시지 API와 서비스 알림톡은 용도를 구분한다. 앱 푸시는 브라우저 푸시로 대체했다고 표현하지 않는다. 웹 푸시를 쓰는 아이폰 이용자는 홈 화면에 추가한 웹앱과 알림 허용이 필요하다.

알림함에는 논리적으로 같은 안내를 한 번 기록한다. 반복 안내는 선택된 앱 또는 웹 경로로 보내고 매번 카톡에도 반복하지 않는다. 수락·참가 확정·경기 취소·경기 방식 변경 같은 중요 안내에는 선택된 푸시와 카톡을 각 한 번 사용할 수 있으며 채널별 중복 요청을 막는다. 기본 푸시 경로는 3.2절의 제안값으로 둔다.

| 대상·상황 | 최초 안내 | 5분 반복 구간 | 중단 |
|---|---|---|---|
| 참가자 결제 대기 | 수락·결제 기한 안내 | 수락 시각부터 기한 직전까지, 최대 30분 | 완료·취소·만료, 확인 중에는 결제 독촉 보류 |
| 주장 미처리 신청 | 새 신청이 오면 즉시 | 최초 안내부터 최대 30분 동안 미처리 신청이 있을 때 | 해당 신청 처리, 모집 마감·경기 취소·시작 |
| 주장 인원 부족 | 시작 30분 전 현재 상태 | 시작 전 마지막 30분 동안 5분 간격 | 부족 해소·모집 마감·경기 취소·시작 |

같은 경기·담당자의 미처리 신청과 부족 인원 안내는 묶어서 보낸다. 이미 진행 중인 30분 반복 구간을 새 신청마다 처음부터 연장하는 안은 사용하지 않는 것으로 제안한다. 구간이 끝났어도 알림함·관리 화면의 미처리 표시를 지우지 않는다. 반복을 멈췄다는 이유로 신청을 자동 수락·거절하지 않는다.

예시: 19시 경기에서 18시 10분 수락하면 결제 기한은 18시 40분이다. 결제 대기 상태가 유지되면 18시 15·20·25·30·35분에 안내하고 18시 40분에는 만료를 처리한다. 18시 22분에 결제가 완료되면 25분 이후 독촉은 보내지 않는다. 18시 50분에 수락하면 결제 기한은 19시이며 18시 55분 안내 후 19시에는 만료를 판정한다.

반복 시각은 서버 기준으로 관리한다. 전달 직전에 권한·최신 상태·유효 시간을 다시 확인하고, 처리 지연으로 지난 반복분을 한꺼번에 몰아서 보내지 않는 것을 제안한다. 알림이 지연되거나 거부되어도 서버의 결제 기한·환불 조건은 바뀌지 않는다. 알림을 눌러 열린 화면도 현재 상태를 조회한다.

알림함 기록, 발송 대기, 제공자 접수, 실패·재시도와 실제 읽음을 구분한다. 제공자가 접수했다고 이용자가 읽었다고 표시하지 않는다. 알림톡 미설정은 연결 준비 상태로 남기고 실제 발송 성공으로 표시하지 않는다.

## 7. 서비스 수수료와 PG 비용

### 7.1. 비용의 구분

| 항목 | 받는 쪽 | 성격 | 현재 상태 |
|---|---|---|---|
| 플랫폼 수수료 | 농구 매칭 서비스 | 초기 0%, 향후 수수료 매출 | 향후 기본 참가비의 총 5~10%, 참가자·팀 반반 안 |
| PG 결제·취소·정산 비용 | 결제 업체 등 | 외부 처리 비용 | 견적 후 부담 방식 결정 |
| 서버·데이터·API 비용 | 해당 제공 업체 | 운영비 | 무료 범위 우선, 비용 발생 시 검토 |

플랫폼 수수료 500원이 그대로 순이익 500원이라는 뜻은 아니다. PG 비용을 서비스가 부담하면 매출에서 비용이 빠진다. 플랫폼 수수료 반반 결정은 PG 비용까지 반반 결정했다는 뜻이 아니다.

초기 화면은 “플랫폼 이용 수수료 무료”로 안내한다. 팀 참가비까지 무료인 경기로 오해하게 표현하지 않는다. 플랫폼 수수료가 0%라도 실결제 단계의 PG 비용이 없어지는 것은 아니므로 견적·부담 주체를 확인해야 한다. 무료 서버 범위와 PG 비용 부담은 별개다. 유료이면 이용하지 않을 수 있다는 사용자의 판단은 초기 수수료 0%의 설계 근거이며, 실제 이탈 원인으로 입증된 결과는 아니다.

### 7.2. 원단위 계산의 제안

모든 금액은 원 단위 정수다. 초기 플랫폼 수수료율은 \(r=0\)이다. 향후 계산 검증에는 \(r=0.05,0.10\)을 사용한다. 기본 참가비 \(B\), 총 플랫폼 수수료율 \(r\)에 대해 다음을 제안한다.

\[
F=\lfloor Br\rfloor,\quad
F_{\mathrm{참가자}}=\left\lfloor F/2\right\rfloor,\quad
F_{\mathrm{팀}}=F-F_{\mathrm{참가자}}.
\]
\[
P=B+F_{\mathrm{참가자}},\quad T=B-F_{\mathrm{팀}},\quad P=T+F.
\]

\(F\)는 전체 플랫폼 수수료, \(P\)는 PG 비용 분담을 반영하기 전 참가자 결제 기준액, \(T\)는 PG 비용 미반영 팀 정산 기준액이다. 첫 테스트 결제는 이 기준액을 사용한다. 실제 PG 비용 부담 방식이 확정되면 최종 결제·환불·정산 계산에도 그 조건을 반영해 검토한다. 전체 수수료 내림 후 반반의 잔여 1원은 팀 몫으로 두는 제안이다. 구현은 정수 수수료율을 사용해 부동소수점 금액 오류를 피한다.

9,900원·5% 예시: 전체 495원, 참가자 몫 247원, 팀 몫 248원, 결제 10,147원, 팀 기준액 9,652원. \(10{,}147=9{,}652+495\)다.

### 7.3. 조건 보존

기본 참가비·수수료율/버전·각 부담액·총결제액·팀 기준액·통화·테스트 여부를 주문에 보존한다. PG 비용은 확인 상태·부담 정책을 분리하고 미확인은 null과 사유로 둔다. 미확인을 0원으로 바꾸지 않는다.

팀 화면은 “PG 비용 미반영 정산 기준액”을 표시한다. 실제 지급액·순이익은 비용과 부담 정책 확정 후 계산한다. 첫 테스트 흐름과 초기 이용 화면은 0%를 사용한다. 5%·10%는 향후 기능의 별도 계산 검증 예시이며 사용자 이용이 늘었다는 이유만으로 자동 과금하지 않는다. 실제 요율·도입 시점·사전 안내는 별도 사업 결정이다.

## 8. 취소·환불·테스트 정산

### 8.1. 정책

운영자가 버전 있는 정책을 제공하고 팀이 선택한다. 정책은 취소 기준 시각·시간 경계·환불률·적용 대상·플랫폼 수수료 반환·경기 취소 처리를 명시한다. 신청 당시 정책과 일시·금액을 보존하고 이후 수정으로 소급 변경하지 않는다.

취소 기준 시각은 권한·대상·상태가 유효한 취소 요청을 서버가 처음 접수한 시각으로 제안한다. 이를 보존해 재시도에도 같은 시간 경계를 적용한다. 브라우저 클릭 시각이나 PG 처리 완료 시각으로 환불률을 바꾸지 않는다.

첫 테스트 제안은 참가자 **총결제액**에 환불률을 적용하고 플랫폼 수수료도 같은 비율로 반환하는 방식이다. 팀의 경기 취소는 누적 환불 목표를 총결제액 전액으로 올리고 이미 환불한 금액을 제외한 잔액만 추가 환불하는 경우까지 테스트한다.

주최자 경기 방식 변경으로 불참하는 참가자도 전액 누적 환불 목표를 적용한다. 변경 안내·불참 선택의 연결을 확인하고 개인 사정 취소 정책과 구분한다. 불참 시점에 이미 일부 환불된 주문은 잔액만 처리한다.

| 테스트 전용 데이터 | 경기 시작까지 남은 시간 | 환불률 |
|---|---|---|
| 정책 A | 2시간 이상 / 2시간 미만 | 100% / 0% |
| 정책 B | 24시간 이상 / 2시간 이상 24시간 미만 / 2시간 미만 | 100% / 50% / 0% |

이 시간·비율은 선택·경계·부분 환불을 검증할 테스트 데이터다. 실제 영업의 적법성이나 팀 대관 사정을 확인한 정책으로 표현하지 않는다. 실결제 개방 전에 계약·운영 정책을 확정한다.

### 8.2. 환불 금액과 상태

환불률 \(q\)는 이번 요청에서 다시 지급할 비율이 아니라 해당 주문의 **누적 환불 목표**다. 제안 테스트 계산:

\[
R^{*}=\lfloor Pq\rfloor,\quad R_F^{*}=\lfloor Fq\rfloor,\quad R_T^{*}=R^{*}-R_F^{*}.
\]
\[
P-R^{*}=(T-R_T^{*})+(F-R_F^{*}).
\]

\(R^{*}\)는 참가자 누적 환불 목표, \(R_F^{*}\)는 누적 반환 플랫폼 수수료, \(R_T^{*}\)는 누적 차감 팀 기준액이다. 이미 완료한 누적액 \(R_0,R_{F,0},R_{T,0}\)을 확인한 뒤 이번 추가 처리액을 계산한다.

\[
\Delta R=R^{*}-R_0,\quad
\Delta R_F=R_F^{*}-R_{F,0},\quad
\Delta R_T=\Delta R-\Delta R_F=R_T^{*}-R_{T,0}.
\]

목표가 이미 달성되었으면 새 PG 환불을 요청하지 않는다. 더 작은 목표가 들어와도 완료된 환불을 되돌리지 않는다. PG 미확정 비용과 실제 팀 지급은 이 계산에 포함하지 않는다.

초기 0% 예시에서 10,000원 결제 후 50%인 5,000원을 환불했다면 팀 취소 시 잔액 5,000원만 추가 환불한다. 플랫폼 수수료 반환액은 두 번 모두 0원이다.

향후 5% 계산 검증 예시에서는 10,250원 결제에서 50%인 5,125원을 환불한 뒤 팀이 경기를 취소하면 100% 목표의 잔액 5,125원만 추가 환불한다. 앞선 플랫폼 수수료 반환 250원·팀 기준액 차감 4,875원에 각각 250원·4,875원을 추가한다. 누적 환불은 10,250원이다.

취소·환불 요청, 처리 중, 완료, 실패를 구분하고 기록을 삭제하지 않는다. 주문마다 한 환불 요청만 처리 중으로 둔다. 앞선 환불 결과가 불명확하면 먼저 PG 조회로 완료액을 정리한 뒤 추가 목표의 차액을 요청한다. 서버 기록과 PG 결과가 맞지 않으면 임의로 맞추지 않고 운영 확인 대상으로 남긴다. 같은 요청 반복이 누적 환불을 늘리지 않게 하며 총환불은 결제액을 넘지 않는다. 결제 전 취소에는 PG 환불이 없다. 팀 취소는 신청별 처리 결과·실패 재처리를 관리한다.

첫 팀 정산은 테스트 계산·기록이고 은행 지급이 아니다. 팀 지급 이후의 실환불 조건은 지급대행 계약과 함께 확인할 후속 단계다.

### 9.2. 이동 결과와 시각

이동 결과는 수단·출발/도착 위치, 제공자/API, 예상 초, 조회시각·적용 시간 기준, 판정·실패 사유를 함께 둔다. 일반 대중교통 API를 미래 출발시각 조회로 표시하지 않는다. 총 경로시간에 도보를 다시 더하지 않으며 대기시간 반영 범위는 공개 문서만으로 확정하지 않는다.

초기에는 조회 세션의 중복 요청 방지와 최소 결과 표시로 설계한다. 별도 경로 캐시 장기 저장·대량 수집은 제공자 허용 범위·보존 조건을 확인한 뒤 결정한다.

DB 일시는 UTC, 표시와 정책 경계는 한국 시간으로 일관되게 관리한다. 경기 날짜를 접속한 날마다 재생성하지 않는다.

### 9.3. 권한·비밀

개인 조건·신청·주문은 소유권을 검증하고 팀 담당자는 자기 승인 팀만 관리한다. 운영자 권한은 자체 프로필 입력으로 얻지 못한다. DB 행별 접근 정책을 작성하고 버튼 숨김만으로 권한을 대신하지 않는다.

공개 클라이언트용 키와 서버·관리자 비밀키를 구분한다. 경로·결제 서버 비밀키와 DB 관리자 비밀키는 서버 설정에 둔다. 로그에 키·전체 결제 응답·불필요한 위치/연락처를 출력하지 않는다.

기기·웹 푸시 등록과 알림함에도 소유권을 적용한다. 안내의 생성·발송은 권한 있는 서버 작업으로 제한하며 회원이 수락·결제 결과 안내를 임의 생성하지 못한다. 수신자는 자기 기록의 조회·읽음 처리를 한다. 로그아웃·계정 변경 시 이전 회원에게 속한 기기로 새 회원의 비공개 안내가 전달되지 않도록 등록 연결을 정리한다. 푸시·알림톡 제공자 비밀 설정은 앱·웹 배포 파일에 포함하지 않는다.

재사용 범위에 관한 비교는 공식 지원 기능과 현재 단일 HTML 구조에서의 재작성 범위를 바탕으로 한 설계 판단이다. Expo도 DOM 구성요소로 웹 화면을 사용할 수 있으므로 재사용이 전혀 불가능하다고 단정하지 않는다. 어느 접근도 설정만으로 현재 카카오·PG·푸시 연동이 완료되었다는 뜻이 아니다. [Capacitor](https://capacitorjs.com/docs), [Expo 웹 구성요소](https://docs.expo.dev/guides/dom-components/).

설치 앱에는 화면 자산을 포함하고 서버에서 최신 상태를 읽는다. 공개 웹 링크와 앱 링크를 연결해 설치 여부·로그인 상태에 따라 같은 경기로 진입하게 한다. 로그인 성공·취소, 카드사 앱 이동·복귀, 앱 종료 후 알림 클릭은 각각 처리한다. 복귀 URL이나 푸시 본문만으로 권한·결제 성공을 판단하지 않는다. [앱 링크](https://capacitorjs.com/docs/apis/app), [인증 복귀](https://supabase.com/docs/guides/auth/native-mobile-deep-linking), [PG 웹뷰](https://docs.tosspayments.com/guides/v2/webview).

지도 Web SDK는 등록된 사이트 도메인에서 사용하는 조건을 따르므로 앱 내부 실행 주소를 일반 웹 도메인과 같다고 가정하지 않는다. 첫 제안은 등록된 HTTPS 웹 도메인의 지도 화면을 별도 구성요소로 제공하고 앱 화면에 포함해 활용하는 방식이다. 메시지 교환은 허용 출처·자료 형태를 검증하고 인증·결제 비밀을 지도 화면에 전달하지 않는다. SDK 도메인 설정과 iOS·Android의 지도 표시·좌표 선택·화면 복귀를 초반 연동 검증 대상으로 둔다. [카카오 지도 설정](https://apis.map.kakao.com/web/guide/). 로그인 SDK를 웹뷰에서 직접 사용할 경우의 외부 앱·팝업 처리는 지도와 별개다. [카카오 하이브리드 안내](https://developers.kakao.com/docs/ko/javascript/hybrid).

카카오 로그인을 우선한다는 의도는 유지한다. iOS의 제3자 로그인에 관한 현재 심사 기준 4.8을 고려해 동등한 대안인 Apple 로그인 추가를 제안한다. 로그인 제공자와 내부 회원 ID를 분리하고, 서로 다른 제공자로 로그인했다고 같은 계정으로 임의 병합하지 않는다. 앱에서 계정 삭제를 시작할 수 있는 경로도 설계하고 남은 참가·환불과 필요한 기록의 처리 기준을 실운영 전에 확인한다. [Apple 심사 기준](https://developer.apple.com/app-store/review/guidelines/).

무료 범위를 우선하되 앱스토어 등록·알림톡 발송 같은 별도 비용을 무료라고 묶지 않는다. 계정·결제 업체·알림톡 준비 상태는 각각 확인한다. 사업자등록을 아직 하지 않은 현재 단계에서 알림톡의 실제 사용 자격·계약·비용이 확보되었다고 표현하지 않는다. 첫 검증은 공유 알림함과 앱·웹 푸시를 진행하고 알림톡은 업체 준비 후 연결하는 순서를 제안한다.

[Apple 3.1.3(e)](https://developer.apple.com/app-store/review/guidelines/), [Google 결제 정책](https://support.google.com/googleplay/android-developer/answer/9858738?hl=en).

NICE의 적용 계약 경로와 KCP의 일반 PG 정가표는 공개 자료만으로 확정하지 않았다. 공개표를 맞춤 견적으로 표현하지 않는다.

## 12. 반대의견·한계·후속 전환

1. 공유 데이터·권한·결제 상태가 필요해 한 HTML의 화면 수정 범위를 넘어선다. 기존 화면을 활용하고 기능별로 나누어 검증한다.
2. 미확인 시설 공개는 오류 위험을 남긴다. 팀·시설·대관을 구분하고 확인 상태·제보·변경 제한을 제공한다.
3. 초기 플랫폼 수수료 0%로도 PG 비용이 생길 수 있다. 향후 반반 수수료는 참가자의 추가 결제와 팀 정산 감소를 만든다. 초기 이용 검증·양쪽 가치·PG 비용 확인 후 실제 과금을 결정한다.
4. 조회 경로 예상시간은 미래 경기일의 정확한 도착을 보장하지 않는다.
5. 팀플레이 분위기는 소개 문구만으로 보장하기 어렵다. 첫 버전은 구체적 진행·교대 정보를 표시하고 실제 이용 후기는 근거와 운영 기준을 갖추는 확장 후보다.
6. 최초 모집팀을 확보해야 실제 반복 이용을 확인할 수 있다. 근거 없는 경기·후기를 실사용 자료로 채우지 않는다.
7. 앱과 웹을 함께 제공하면 코드·데이터 공유가 가능해도 양 OS·웹의 로그인·지도·결제 복귀·푸시 검증은 남는다. 기존 HTML을 앱 파일에 포함하는 것만으로 완성·스토어 승인을 보장하지 않는다.
8. 5분 반복은 즉시 대응에 도움이 될 수 있지만 구간 제한·묶음·중단이 필요하다. 푸시는 권한·기기·네트워크 상태에 따라 지연될 수 있고 결제 기한까지 전달을 보장하는 수단으로 약속하지 않는다.
9. 플랫폼 기록만으로 실제 현장 경기·참석을 확정하기 어렵다. 주최자 안내의 출처·변경 이력·제보를 관리하되 운영자가 직접 확인한 것으로 표현하지 않는다.

실결제·실정산 전환에는 업체 계약·심사, 팀 수령 구조, 비용·환불 정책, 운영 처리 담당, 실제 API·사용량 설정, 사용자의 최종 전환 확인이 필요하다. 테스트 키 변경만으로 완료되는 단계가 아니다. 스토어 공개와 알림톡 실제 발송도 각각 계정·기기 검증·설정·비용을 확인하는 별도 단계다.
